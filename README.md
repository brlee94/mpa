# MPA Mail Tools · 웹 EML → PST 변환기

Windows와 macOS의 **브라우저 안에서** EML을 Unicode PST로 변환합니다. 실행 파일 다운로드, 프로그램 설치, Outlook 설치, 별도 서버가 필요하지 않습니다. 선택한 메일과 첨부파일은 서버로 전송하지 않습니다. 변환된 PST만 사용자가 저장합니다.

## 사용

최신 버전 전용 주소: **https://brlee94.github.io/mpa/releases/merge-v5/**. 화면 상단에 **버전 5**가 표시됩니다. 루트 주소의 캐시와 분리한 전체 앱을 이 경로에 게시합니다. 새 보고서는 `앱 버전` 열에 `merge-v5`를 기록합니다.

1. 배포된 웹사이트에서 EML 파일을 드래그하거나 **폴더 선택**을 누릅니다.
2. 결과 파일 이름과 원본 EML 첨부 여부를 선택합니다.
3. 총 32MB 이하이면 **PST로 변환하기 → PST 저장하기**로 저장합니다. 총 32MB를 넘으면 **저장 폴더 선택** 후 변환하세요. 새 작업 폴더 안에 여러 PST가 차례로 저장됩니다.

폴더 선택 시 폴더 구조를 유지합니다. `.eml`, `.EML`, `.eml.15`를 지원합니다. Windows에서 보이는 `Outlook.File.eml.15`는 일반 EML의 형식 이름인 경우가 많습니다.

권장 브라우저는 Windows/macOS의 최신 Chrome 또는 Edge입니다. OS와 무관하게 WebAssembly 및 로컬 파일 선택 기능을 사용합니다. Safari용 엔진 다운로드가 현재 빌드 환경의 네트워크 정책에 차단되어 Safari 실행 검증은 하지 못했습니다.

## 여러 PST를 하나로 합치기

1. 버전 5에서 **PST 합치기**를 누르고 PST 2~256개(합계 4GiB 이하, 읽는 메일 100,000개 이하)를 선택합니다.
2. 결과 이름과 **동일 폴더의 중복 메일 제외** 여부를 선택합니다. 중복 제외는 기본값이며, Message-ID만 비교하지 않고 폴더 경로·주요 메일 정보·본문·첨부 내용을 SHA-256으로 대조합니다. 내용이 다르거나 폴더가 다르면 보존합니다.
3. 결과 저장 폴더를 선택하고 **하나의 PST로 합치기**를 누릅니다. 새 작업 폴더에 PST 하나가 저장됩니다. 원본 PST와 이전 결과는 변경하지 않습니다.

이 앱에서 생성한 메일 PST가 검증 대상입니다. 메일이 있는 폴더 경로와 상위 구조, 텍스트/HTML, 발신자·To/Cc/Bcc·날짜·Message-ID, 일반 첨부·인라인 이미지·원본 EML을 옮깁니다. 연락처·일정·작업, RTF 전용 본문, Outlook 메시지 형식의 내장 첨부는 지원하지 않으며 발견하면 전체 병합을 중단합니다. 잘못된 입력이나 저장 실패 때 일부 메일만 들어간 결과를 게시하지 않습니다.

PST 병합은 Windows/macOS의 최신 Chrome/Edge에서 동작합니다. Web Worker가 별도 .NET 런타임을 실행하고, 입력 PST 하나와 작성 중인 결과를 OPFS 임시 디스크에서 처리합니다. 읽기와 첨부 복사는 작은 블록으로 스트리밍하며 결과 전체를 RAM에 적재하지 않습니다. 완료·중지 시 작업자를 종료해 병합 엔진의 WASM 메모리를 해제하고 임시 파일을 삭제합니다. 최종 결과는 파일 스트림으로 선택 폴더에 복사합니다. 임시 저장소에 대략 원본 합계+가장 큰 입력 PST만큼, 결과 폴더에 병합 파일만큼의 여유 공간이 필요합니다. 임시 저장 공간 부족도 명확한 오류로 처리합니다. 결과 파일 내부 한도는 8GiB이며 입력 합계는 4GiB입니다.

## 보존 범위와 한도

- 텍스트 및 HTML 본문, 한글 헤더, 보낸 사람, To/Cc/Bcc, 보낸 날짜와 수신 날짜, 메시지 ID와 MIME 헤더를 저장합니다.
- 수신 날짜는 첫 번째 유효한 `Received` 날짜를 사용하며 없으면 `Date`를 사용합니다. 유효한 날짜가 없으면 변환 시각을 사용합니다.
- 일반 첨부, 인라인 이미지 Content-ID, 첨부된 EML을 보존합니다. 기본값으로 원본 EML 전체를 별도 첨부하므로 원본을 그대로 추출할 수 있습니다.
- 읽음 상태의 일반 메일로 저장합니다. S/MIME 복호화, winmail.dat 내부 추출, 원래의 읽음 상태 복원은 하지 않습니다. 원본 EML을 보존하는 옵션을 권장합니다.
- **한 번에 1,000개, 원본 합계 4GiB, 파일당 100MiB**까지 선택합니다. 총 32MiB 초과는 Windows/macOS의 최신 Chrome 또는 Edge에서 저장 폴더의 쓰기 권한을 허용해야 합니다. 입력 버퍼는 파일 크기에 맞추고 첨부 버퍼의 추가 복사를 줄였습니다. 전체 메일이나 전체 결과를 한꺼번에 메모리에 보관하지 않습니다.
- 대용량 작업은 **원본 합계 약 32MiB 또는 64개 단위의 여러 Unicode PST**로 저장합니다. 파일 하나를 두 PST로 쪼개지는 않습니다. 각 PST는 1MiB 블록을 사용하는 임의 접근 버퍼로 작성해 큰 연속 메모리 할당과 용량 확장 시 전체 복사를 피합니다(한도 384MiB). 256KiB씩 JavaScript에 전달하고 디스크 쓰기 완료를 기다린 뒤 다음 블록을 보냅니다. 각 메일·PST 처리 후 사용한 버퍼를 주기적으로 수거합니다. 큰 메일 한 개는 별도 PST로 저장하므로 32MiB를 초과할 수 있습니다. 단일 4GiB PST를 만드는 기능은 아닙니다.
- 선택한 저장 폴더 아래에 이름·시각·임의 식별자를 조합한 새 작업 폴더를 만들고 `이름-001.pst`, `이름-002.pst`처럼 저장합니다. 기존 파일은 덮어쓰지 않습니다. 원본 EML 보존 옵션을 켜면 결과 합계가 원본보다 커질 수 있으므로 충분한 디스크 공간이 필요합니다.
- 잘못된 EML은 제외하고 CSV 보고서에 남깁니다. 모든 파일이 실패하면 PST를 내보내지 않습니다. 중지하거나 저장 오류가 생기면 아직 저장하지 않은 부분은 폐기하고, 디스크에 저장을 마친 PST는 보존합니다. 폴더 저장 성공 수는 저장을 마친 메일만 집계합니다. 보고서에 전역 중단 원인, 파일별 처리 상태, 원본 바이트 수와 저장 PST 경로를 기록합니다. 이전 보고서로 완료 항목을 제외한 작업은 누적 저장 수를 표시합니다.
- 탭을 닫으면 메모리상의 입력과 결과는 사라집니다. 기존 PST를 수정하거나 원본 파일을 변경하지 않습니다. 같은 화면에서는 **미저장 메일만 다시 변환**으로 저장 완료 항목을 제외할 수 있습니다. 새로고침 후에는 동일한 EML 전체를 선택하고 **이전 보고서 불러오기**로 CSV를 적용하세요. 전체 경로·개수 및 새 보고서의 바이트 크기가 일치해야 합니다. 기존 3열 보고서는 크기 정보가 없어 경로로 대조하므로 동일한 원본을 선택해야 합니다. 실제 기존 PST의 존재나 내용까지 검사하는 기능은 아니며, 이전 PST도 함께 보관해야 합니다.
- PST 생성 엔진은 Unicode PST를 작성합니다. 엔진의 알려진 제약으로 Outlook 검사 도구가 메시지 크기 재계산이나 검색 폴더 관련 안내를 표시할 수 있습니다. [PstBuilder 설명](https://github.com/ml-ls/PST-Builder#two-harmless-scanpst-notes)을 참고하세요.
- Windows/macOS 지원은 **변환 환경**을 뜻합니다. PST를 열거나 가져오려면 이를 지원하는 앱이 필요합니다. Mac용 새 Outlook은 PST 가져오기를 지원하지 않을 수 있습니다.

## GitHub Pages 배포

`gh-pages` 브랜치 루트에 이미 빌드된 정적 사이트를 게시합니다. 런타임 서버와 비밀 값은 필요하지 않습니다.

저장소 관리자가 [Settings → Pages](https://github.com/brlee94/mpa/settings/pages)에서 다음 값을 저장하면 됩니다.

- **Source:** Deploy from a branch
- **Branch:** gh-pages
- **Folder:** / (root)

활성화와 배포가 완료된 뒤의 기본 주소는 `https://brlee94.github.io/mpa/`입니다. 저장소의 Pages 설정에서 실제 게시된 주소와 배포 결과를 확인하세요. `gh-pages`에 파일을 업로드한 것만으로 사이트 활성화 성공을 뜻하지는 않습니다.

현재 환경은 Git 전송으로 브랜치 업로드가 가능하지만 GitHub 관리 API(`api.github.com`) 및 사이트 도메인에 대한 접근이 네트워크 정책에 차단되어 있습니다. 따라서 Pages 설정 변경과 공개 사이트 응답 검증은 이 환경에서 직접 수행할 수 없습니다. 저장소 관리자의 위 설정이 필요합니다.

## 빌드

개발할 때만 .NET SDK 10.0.402, Node.js, Python 3가 필요합니다. 사이트 사용자는 설치하지 않습니다.

```bash
bash scripts/publish-web.sh
```

`artifacts/web/wwwroot`가 배포할 전체 정적 사이트입니다. 게시 스크립트가 Python 3로 `AppVersion.Id`에 해당하는 `releases/<버전>/` 경로에도 모든 실행 파일을 복사합니다. 전용 주소는 루트의 이전 HTML·실행 파일 캐시와 분리되어 있으며, `release.json`에 게시 버전과 경로를 기록합니다. 새 배포는 새로운 버전 ID와 경로를 사용하세요. 하위 경로(`/mpa/`)에서 동작하도록 상대 base URL을 사용합니다. `.nojekyll`을 포함해 `_framework` 디렉터리가 Pages에서 제외되지 않게 합니다. 잠금 파일은 일반 빌드와 브라우저 배포용을 구분합니다.

로컬 확인:

```bash
python3 -m http.server 8765 --directory artifacts/web/wwwroot
```

브라우저로 로컬 서버에 접속하면 됩니다. 공개 사이트는 HTTPS를 사용하세요.

## 검증

Linux의 실제 Chromium에서 파일 선택 → 브라우저 WebAssembly 변환 → PST 저장을 실행한 뒤, **작성 엔진과 독립적인 XstReader**로 PST를 다시 읽어 검증했습니다.

검사 범위: Unicode PST 헤더, 실패 EML 제외, 한글 텍스트/HTML, 보낸 사람/To/Cc/Bcc/메시지 ID, 보낸 시각과 수신 시각, 첨부파일 바이트와 CID, 중첩 EML, 원본 EML의 바이트 보존, CSV 보고서, 원본 첨부 옵션, 잘못된 입력, 폴더 구조, 좁은 화면, 크기 제한, 중지, 메일 외부 전송 없음.

```bash
npm ci
# 배포 파일을 제공하는 로컬 정적 서버를 먼저 시작합니다.
WEB_URL=http://127.0.0.1:8765/ npm run test:web
WEB_URL=http://127.0.0.1:8765/ npm run test:web:large
WEB_URL=http://127.0.0.1:8765/ npm run test:web:recovery
WEB_URL=http://127.0.0.1:8765/ npm run test:web:stress
WEB_URL=http://127.0.0.1:8765/ npm run test:web:merge
WEB_URL=http://127.0.0.1:8765/ npm run test:web:merge-large
```

`CHROMIUM_PATH`는 기본 `/usr/bin/chromium`입니다. 다른 경로이면 지정하세요. `DOTNET`으로 SDK 실행 파일 경로를 지정할 수 있습니다. `TEST_WEBKIT=1`로 WebKit도 실행할 수 있으나 해당 Playwright 브라우저 설치가 먼저 필요합니다. 검증 스크립트는 독립 PST 리더를 자동으로 빌드하고 `artifacts/web-checks`에 출력과 스크린샷을 남깁니다. 대용량 검사는 `artifacts/web-large-checks`에 결과를 남깁니다.

대용량 검사의 합계 4GiB 경계는 희소 파일의 메타데이터로 검사하며, 전체 4GiB 메일 본문을 변환하는 검사는 하지 않습니다. 실제 대용량 변환은 약 43MiB EML 세 개와 100MiB에 가까운 EML 한 개를 사용합니다. 복구 검사는 두 번째 PST 저장 시 디스크 오류를 주입하고, 앞선 64개 보존 및 나머지 67개만 재시도하는 동작과 이전 형식 CSV(638개 중 286개 완료)를 적용해 352개만 생성하는 동작을 확인합니다. 장시간 검사는 약 1.25GiB의 합성 EML 638개를 한 번에 변환합니다. 각 PST를 독립 리더로 읽고 모든 첨부와 원본 EML의 SHA-256 및 누락·중복 여부를 검사합니다. 자동화에서는 운영체제의 폴더 선택 대화상자만 대체하며, 실제 브라우저의 디스크 기반 FileSystemDirectoryHandle(OPFS)에 저장합니다. 장시간 검사는 CDP로 테스트용 OPFS 한도만 8GiB로 설정합니다. 사용자 선택 폴더의 저장 방식은 변경하지 않으며, 저장 오류에 대한 검사는 별도로 실행합니다. 사용자 이메일은 테스트나 저장소에 포함하지 않습니다.

PST 병합 검사는 별도 읽기 엔진으로 폴더·본문·수신자·시간·첨부 바이트를 대조하고, 동일 폴더의 중복 제외 및 다른 폴더/다른 내용 보존, 중복 보존 옵션, 중지·잘못된 입력·미지원 항목·저장 실패 시 결과 폐기와 임시 파일 정리, 원본 해시 불변을 검사합니다. 대용량 병합 검사는 8MiB 첨부가 포함된 메일 288개(첨부 합계 2.25GiB)를 세 PST에서 하나로 합치고 2GiB를 넘는 오프셋과 모든 첨부 SHA-256을 확인합니다. 일반 브라우저와 같은 디스크 기반 OPFS를 사용하는 임시 지속 프로필에서 테스트용 OPFS 할당량만 12GiB로 설정하며, 작업 완료 후 임시 디스크 삭제와 병합 단계 직후 샘플한 관리 힙 크기도 확인합니다.

Windows/macOS의 실제 Outlook에서 파일을 여는 검증은 이 Linux 환경에서 실행하지 못했습니다. 최초 사용 시 소량의 메일로 결과를 확인하세요.

## 구조 및 라이선스

- `src/EmlToPst.Web`: 한국어 Blazor WebAssembly UI. 메일 업로드 API 없음.
- `src/EmlToPst.Pst`: 메모리상의 PST 생성 및 MIME → 메시지 매핑. PstBuilder 1.3.0 사용.
- `src/EmlToPst.Core`: MimeKit 기반 MIME 파싱 및 첨부 처리.
- `src/EmlToPst.Merge`: 디스크 스트림 기반 PST 병합·중복 검사.
- `third-party/XstReader.Streams`: MS-PL 읽기 엔진의 스트림·동기 정리 수정본. 원본 출처와 변경 내역을 포함합니다.
- `tests/web`: 브라우저 및 독립 PST 읽기 검사.
- `tests/EmlToPst.Inspect`: 개발 검증용 XstReader. 웹앱에는 포함하지 않음.
